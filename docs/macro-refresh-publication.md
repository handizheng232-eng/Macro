# 宏观刷新与历史研究发布的分离验收

历史研究的旧回执绑定当时的整份宏观 JSON。直接把最新宏观数据放入旧版研究门禁，会把正常的 generatedAt 和历史修订误判为研究篡改。不得通过更新旧回执或删除测试解决。

## 两个独立验收面

- **当前五份宏观数据**：从已授权来源取数，逐序列核身份、单位、频率、真实首期和量级；保留原始响应。全量现行数据测试在当前工作树、当前五个候选上运行。新的 `release/macro-refresh-publication-01.json` 绑定实际候选的精确字节、取数时间和此次构建的所有静态资源。
- **既有研究版本**：`release/snapshots/macro-research-baseline-1a0231d.zip` 仅含旧回执白名单内已公开的源码、资料元数据和静态图，不含私有原件、token或 data/raw。整个包的 SHA 固定在 `macro_publication_snapshot.py`。在临时目录恢复精确旧字节后，运行未改变的历代门禁及其测试，并重建各自当时版本的资产；不拿新 JS 冒充旧版本。

`run_data_tests.py` 仍发现全部 `scripts/test_*.py`。只有显式列举的版本化发布测试被分配到旧版本环境，不 skip、不删除、不减少断言。每个已发现测试 ID 必须在真实子进程输出中恰好执行一次，执行数必须等于发现数；历史测试源码与冻结版本不符时拒绝执行，而不是悄悄使用旧测试。其余测试全部对当前代码与数据运行。

## 每次数据发布

1. 获取五个隔离候选，备份原始响应及原有五文件。
2. 完成原始数据核验后推广候选；执行当前数据测试、全部前端测试、lint、build和真实浏览器检查。
3. 在用户已授权发布且本轮页面检查实际通过后，用 `verify_macro_refresh_publish.make_receipt` 生成本次新数据回执（`authorized=True, qa_complete=True`）。测试里的内存回执只是测试夹具，不能当作页面验收证据。
4. 新回执与必要基础设施修改单独提交；五个宏观 JSON 保持独立数据提交。CI执行 `verify_macro_refresh_publish.py --legacy-tests --dist dist`。
5. 对精确SHA的Pages成功部署进行读回；生产HTML/资源必须与本次CI产物逐字节一致，并复验九路由及温度表交互。

仅五个宏观 JSON 被允许正常换版。其它已发布研究文件仍逐字节受旧版本约束；本次必要的执行器、刷新脚本、工作流和换行配置修复须显式列入新回执的基础设施白名单，不能用该白名单授权修改研究内容。新增研究阶段仍需要自己的独立授权与版本化门禁。

Windows工作树使用明确的LF文本策略，原有 `-text` 原字节研究文件与SVG规则保留。检验旧版本必须以Git原始字节或已核验的公开快照为准，不重写历史回执适配CRLF。
